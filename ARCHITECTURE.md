# FinchLearn Studio Architecture

Whiteboard style (issue #52): a scene may carry a `whiteboard` style (board surface as scene data) and shape, text, and image elements may carry a `drawOn` treatment (duration, hand style, optional erase). In the editor's OCF project model the same data lives under the `x-finch-studio` extension on objects and scenes. Draw progress, stroke reveal, and wipe math are pure functions of time in packages/motion (whiteboard.ts), sampled identically by the stage and by both export paths; objects without the treatment are untouched.
Cue markers (issue #64): scenes carry optional cue markers (knowledge check, branch, modal, chapter) with the payload each type needs (an inline question, branch choices, or a popup reference). The schema OCF mapping exports them as structured OCF cue-point metadata: native cue points (with question or branch cue actions, and a cue-point trigger opening the modal) placed once on the scene's first footage object, plus a lossless copy under that object's extensions["x-finch-studio"].cueMarkers (on the first mapped object when a scene has no footage). The editor authors the same CueMarker shape on its VideoScene objects under `cueMarkers` (an editor-owned scene field, since @finch-studio/core's VideoScene has no marker field yet) and applies the identical conversion when a project is handed to FinchLearn. Marker fields are all optional beyond time and type, so projects written before #64 parse exactly as before. The FinchLearn player binding for these cue points lives in open-course-format #629.
## Stage aspect (issue #13)
- A project carries one stage aspect (`VideoProject.aspect` in @finch-studio/core, mirrored on the Studio schema's `StudioProject.aspect`): "16:9", "9:16", or "1:1". The field is additive; projects without it open as 16:9.
- Object positions live in the aspect's stage coordinate space (@finch-studio/animation `STAGE_DIMENSIONS`: 1280x720, 720x1280, 720x720). The stage canvas, the safe-area preview (schema `safeZones` for the current aspect), and both export paths frame from that one space; export presets keep their resolution tier and take their shape from the project aspect.
- Switching aspect in place reframes like `duplicateProjectAs` (#62): positions scale by the frame ratio, sizes shrink to fit, and elements clamp inside the new frame so nothing is lost. Objects found outside the frame (for example from hand-edited JSON) stay in the project and are marked "Outside frame" on the stage.
Colour correction (issue #46) is non-destructive metadata: five sliders (exposure, contrast, temperature, tint, saturation) defined in packages/schema/src/colorCorrection.ts, carried on schema elements as the optional `colorCorrection` field and on editor objects under extensions["x-finch-studio"].colorCorrection. One canonical 4x5 colour matrix (colorMatrixFor) drives every render path: the stage applies it via an SVG feColorMatrix filter, the browser exports apply it per pixel to a corrected copy of the image, and the server render node runs the same export code, so all three stay in parity. Absent or all-zero is neutral and renders exactly as before.

## Layout
- packages/core (@finch-studio/core): OCF types and animation runtime, extracted verbatim from @ocf/core (types.ts, animations.ts). Pure TypeScript, no React, no DOM. See packages/core/EXTRACTION.md.
- packages/animation (@finch-studio/animation): scene time infra, dialogue scheduling, the TTS provider seam, and the OCF video project model, extracted from @ocf/animation-studio. Character art did NOT move; the CharacterFigure component is the seam for the new rigged characters. See packages/animation/EXTRACTION.md.
- packages/schema (@finch-studio/schema): the Studio project schema v1 (the product's own format), timing math, validation, and the OCF mapping with its sidecar (stored under extensions["x-finch-studio"] when embedded). Scene elements include a lottie kind (issues #97, #99, #100) that maps to a real OCF lottie object, so it round trips with or without the sidecar.
- apps/editor/src/lottie: the shared deterministic Lottie renderer (issues #97, #99, #100). lottieCore samples a Lottie animation at an exact frame and renders it to SVG from scene clock time only; dotLottie reads .lottie containers without a zip dependency; lottiePack catalogues the bundled Generative Icons set (MIT, licenses.json beside the assets in apps/editor/public/lottie); generativeIcons is the live Browse client. The stage preview, both client export paths, and the server render host all render through lottieCore, so Lottie frames cannot drift between preview and export.
- packages/audio (@finch-studio/audio): the audio engine core (track roles, ducking, envelope and loudness math) plus Clean Voice (#29): a per clip cleanup chain (rumble highpass, low shelf cut, gate, presence lift, de-ess cut, light compression, makeup gain) described as plain data and built from Web Audio primitives, so preview playback, both client export paths, and the server render host (which drives the same export code) all apply it identically. The setting lives in the clip's x-finch-studio metadata, defaults OFF, and OFF is identity: no nodes are created and the clip renders exactly as before.
- packages/characters (@finch-studio/characters): the rigged character system. One standard skeleton for every character in every style family; actions are keyframed data sampled through the motion engine; expressions and viseme lip sync are face data; style families are art packs over the same parts (A Clean Corporate Flat is the launch family, B Warm Storybook Soft the approved secondary set, D Bold Ink Editorial the second full style family from issue #53: ink outlines and angular tapered parts over the same skeleton, with its own bundled prop and background pack in the editor content catalogue). RiggedCharacter renders the same SVG on the stage and in exports. The editor maps legacy character ids onto the studio cast until the picker is refreshed; user rigged characters (#74) plug into the same skeleton. Custom rigging (#74) lives in the characters package as pure data and functions: rigging.ts (pin sets normalized to the source image, heuristic first pass joint detection, the pin to bone map derivation with user adjustable proportions, the segmented parts versus single image puppet warp decision with its honest quality notes, face packs riding the expressions and viseme model, and re-derivation that preserves user pin adjustments as offsets from detection when the editable base image changes), svgTemplate.ts (the downloadable named layer SVG template and its structural matcher; a matching upload rigs itself at full part quality with zero pins), and sourcePort.ts (the character source port; the generated kind is a seam in this package, bound in the editor to the AI asset generation service by apps/editor/src/generatedCharacterSource.ts, so it generates when that service is configured on the build and fails honestly until then). CustomCharacterFigure renders a custom def posed by any action in the same 200 x 400 stage space as RiggedCharacter, segmented parts by forward kinematics over the user's bone map or the single image in clipped bands for puppet warp, and the editor uses it on the stage and in export frames so previews and exports cannot drift. Custom defs persist through the editor's localStorage backed user library (apps/editor/src/customCharacters.ts, key finch-studio.user-characters) and travel inside scene objects under the x-finch-studio extension, so no schema change was needed and a saved character opens intact in any project.
- packages/translation (@finch-studio/translation): project translation variants (issue #54). The 20-language set as data, a swappable translation provider port (first binding: Google Cloud Translation v2, key supplied by the caller from configuration, secret names only in code), the catalogue voice mapping rule, and the variant builder: a full project copy with fresh ids, source linkage under the project's extensions["x-finch-studio"], translated text/bubbles, re-voiced and re-timed dialogue, and a caption track in the variant language riding the existing caption model. Unconfigured providers fail honestly; nothing fakes a translation.
- apps/editor (@finch-studio/editor): the editor app, extracted from @ocf/video-studio. One zustand store; all project mutations go through the store.
- packages/ai-assets (@finch-studio/ai-assets): AI asset generation (issues #93 and #95). Style family resolution (scene default, then project, then Direction A; explicit picks and custom character sets override), baked in output defaults per asset kind (flat vector look, transparent for props and objects, full bleed stage sized rectangles for backgrounds), a swappable generation provider port following the translation package pattern (endpoint binding configured by the caller; the honest unconfigured binding is the shipped default, nothing fakes output), provenance stamping in the stock asset discipline, and a generate flow that checks the existing FinchLearn AI allowance through an injected port (no new credit system) and saves every asset into the user media library as a MediaAsset with source "user" plus an additive `generated` provenance record. Generated assets place on the stage as normal image objects with provenance in their x-finch-studio extension metadata. The editor wiring lives in apps/editor/src/aiAssets.ts with the Generate tab in the media panel.
- packages/standalone-export (@finch-studio/standalone-export): standalone export packaging (issue #56). Pure, deterministic, dependency-free modules: a STORE zip writer, PNG inspection, SCORM 1.2 and 2004 package builders (embedded rendered MP4 plus a poster frame; completion when the video ends, with a 95 percent playback fallback; no server or account needed at runtime), a PowerPoint builder (one slide per scene, scene frame as the slide image, scene title and dialogue in speaker notes), and a PNG scenes zip builder. It never renders: scene frames and video come from the editor's shared export renderer (apps/editor/src/videoExport.ts, renderProjectSceneFrames and exportMp4Project), so standalone outputs cannot drift from the MP4 paths.
- packages/mcp-video (@finch-studio/mcp-video): the service core behind the FinchLearn MCP server's video tools (issues #50 and #66): the Keeper plan gate (mirrored semantics, injected plan resolver), project/scene/dialogue/narration/footage/export operations over ports that adapt the shipped surfaces (studio_projects/studio_exports, finch-media, finch-render, the narration stack), parameterized template rendering, and the embed port seam for #49/#629. The tool definitions are shaped like the MCP server's own tool files; the server-side wiring lives in the OCF repo. Contract: docs/mcp-contract.md.

## Project schema
One versioned JSON document per project (schema.ts): scenes with timed elements (footage, character, image, text, chart, shape, audio, lottie), dialogue lines with voice bindings and reserved word timings, global music, caption tracks, cue markers (OCF knowledge checks and branching), snapshots for non-destructive versioning. Assets are R2 keys only, never bytes and never viewer identity. Lottie elements are the one exception to the R2 only rule for their payload: a user import may carry its parsed animation JSON or a data URI inline so the project stays self contained, alongside the packId and R2 asset forms. The editor's VideoProject (packages/core) carries the same optional extensions bag at project level; translation variants record their source linkage there under extensions["x-finch-studio"] (additive, absent on plain projects).

Scene and object effects are named presets in the shared animation engine. The Studio schema mirrors these presets, which expand to timeline tracks at render time. The editor exposes preset, delay, and duration controls only.

Footage elements (issue #25) carry non-destructive edit metadata: sourceInMs / sourceOutMs trim, speed (0.5x to 2x), and volume, plus optional freeze (a held source frame for a set duration), crop (a source rectangle in unit fractions), and pipLayout (full, corner, and split presets that set the element's stage position). All of it resolves through the one resolver in packages/schema/src/footage.ts (segments, timeline duration, source time at a timeline offset, crop clamping, PiP rectangles); an element's durationMs is the resolved timeline duration. The editor stores the same edits on video objects under the x-finch-studio extension (apps/editor/src/footageEditing.ts) and the stage, both browser export paths, and the server render (the same export code in headless Chrome) all consume that resolver, so preview and exports cannot diverge. Legacy footage without the optional fields resolves exactly as before.
Motion graphics (issues #98 and #99, built-in pack): packages/animation's motionGraphics module builds parameterized title cards, lower thirds, and callouts as groups of ordinary timeline objects whose members carry coordinated named presets plus their parameters under extensions["x-finch-studio"].motion; Ken Burns framing rides the same bag and expands through the shared preset engine; kinetic text presets (typewriter, word by word, line by line) expand to a deterministic per-unit reveal schedule, optionally paced by the schema's reserved dialogue word timings. Chart stings are named presets in the shared engine. Scene transitions stay on the existing TransitionKind model, not presets. The stage renderer and the export renderer sample the same toolkit functions, so frames cannot drift.

## State patterns
- The editor store owns the open project; components never mutate project JSON directly.
- Undo is one stack across scene and timeline edits.
- Scene duration derives from the longest timed element, narration, or character movement, with a half-second minimum. Untimed scenes default to five seconds and retain shorter durations after ripple deletion.
- Per-scene voiceover (#31): a recorded take chosen in the Dialogue panel lands as an audio object marked as the scene voiceover in its `x-finch-studio` clip metadata, timed from the scene start for the take's length, and the script lines are re-timed to the take, so the derivation above sets the scene duration from the take. A scene with a voiceover clip uses the recording in preview and export instead of generated narration for its lines.

## Rendering
Preview in the browser on proxy media. Two export paths, both held to 1:1 parity with the stage canvas (golden frame tests): client WebCodecs plus Mediabunny as the default for standard timelines, and server FFmpeg workers for heavy footage, unsupported codecs, and headless MCP renders. Server renders are split by scene with segment caching.

## Accessibility (Section 508, issue #63)
The export dialog runs a pre-flight pass (apps/editor/src/accessibility.ts) over the project before export: text contrast against its effective background (scene background, or the topmost shape under the text), minimum font size, and flash rate from authored opacity animations (WCAG 2.3.1, more than three flashes in any second). Findings are grouped per scene with a jump to scene action; the pass reports and never blocks an export by itself. Audio clips carry an engine role in their x-finch-studio metadata (role, plus descriptionText for the Audio Description script). The description role in @finch-studio/audio auto-ducks primary audio in a mixed export, or exports as a secondary WAV audio track plus a timed VTT track alongside captions (planAudioExport in packages/audio is the shared planning layer for both render paths).

## Media
All media lives in Cloudflare R2 behind the key checked media worker: Finch Stock, Unsplash (via the worker proxy, attribution stamped), and the user media library. Ingest generates a 720p proxy, waveform peaks, and a thumbnail strip. Audio peak arrays and edit metadata use the `x-finch-studio` object extension; peak values are normalized numbers, not media bytes. Browser screen and webcam recordings (packages/media recording core, Record tab in the media panel) enter through the same ingest path as user source video assets and land in a scene as normal footage objects.

Text based rough cut (#45): a clip's ASR transcript (the #43 contract, stored under `extensions["x-finch-studio"].transcript` on the clip object, word times in source milliseconds) can be edited as text in the editor's Rough cut panel (`apps/editor/src/roughCut.ts` plus `RoughCutPanel.tsx`). Deleting a sentence or a word range maps the words to scene times (clip start plus word time minus the clip's source offset) and ripple deletes that media through the same clip editing model as the timeline and silence tightening: audio targets reuse `rippleDeleteAudioRegion`, video targets mirror it with `sourceInMs`. Results are ordinary split clips, source media is never rewritten, each deletion is one commit on the shared undo stack, and clips without a ready transcript show an explanation instead of the editor.

Speech recognition (#43): voice clips and speech footage are transcribed at ingest by the finch-asr service (`services/asr`, VPS, alongside finch-render; FFmpeg extracts audio, a Whisper style engine returns word level timestamps). The transcript contract lives in `packages/media/src/transcript.ts` (mirrored in `packages/schema`): a clip scoped `ClipTranscript` with word start/end in ms into the source clip, confidence only where the engine reports it, stored under `extensions["x-finch-studio"].transcript` on the asset or object that carries the clip. Re-runs key off the clip content hash; unchanged clips never re-run. Captions (#44) and the text based rough cut (#45) consume this contract.

## Multicam (#47)
A footage scene may carry one multicam group (packages/schema `multicam.ts`, additive `StudioScene.multicam`; editor scenes carry the same group as `scene.multicam`): up to 3 angles, each pointing at a footage element / object by id, plus segments that choose the on-screen angle over scene time. Angles sync by audio cross-correlation over the ingest peaks (packages/media `multicamSync.ts`, pure, no decoding in the editor), recording an honest offset plus confidence / quality and a manual nudge the user can adjust. Segment resolution is the single shared rule: the stage, both browser export paths, and the server render host (which runs the same export code) all resolve through it, and render segment cache keys hash the scene JSON so a cut or offset change re-renders. Scenes without a group behave exactly as before; footage trim / speed / crop (#25) stay on the referenced element / object, not in this model.

## Surfaces and integration
- studio.finchlearn.com: signed out visitors get the landing page, signed in users get the studio hub at the root with no redirect flash; auth is shared across .finchlearn.com (Supabase).
- Embedded mode: a signed handoff from FinchLearn opens the editor directly in a popup; Save & Return binds the saved library asset into the course video block. The handoff/return contract is pinned in docs/embed-contract.md and implemented in apps/editor/src/embed.ts (verification fails closed; Finish posts the return payload to the handoff's return origin and persists it under the local return key; a render still running returns a rendering payload first and a ready payload when the render lands).
- MCP: the FinchLearn MCP server gains video tools over this same project JSON, Keeper and up.
